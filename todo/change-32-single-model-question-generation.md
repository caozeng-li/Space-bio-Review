# Change 32: 单一强模型生成全局问题列表

状态：实现已完成，默认路径已替换；科学质量验收未通过。日期：2026-10-13。实际结果见 [实施记录](change-implementation-results.md)。

## 本轮顺序与约束

按 Change 32 -> 33 -> 34 -> 35 -> 36 实施，不走 OpenSpec。

1. 本文：输入准备、专家配置投影、单一问题生成契约及提示词。
2. [Change 33](change-33-ranked-question-dispatch.md)：全局排序、代码截取、确定性派工与上下文。
3. [Change 34](change-34-question-generation-lifecycle.md)：生成与生效的生命周期，以及 mytest22 的局部故障修复。
4. [Change 35](change-35-retire-question-replanning.md)：删除旧起题、归并、增量再规划链路，接入默认入口。
5. [Change 36](change-36-local-question-generation-acceptance.md)：固定局部验收矩阵与交付决定。

本轮取代 Change 22-31 中“先收集问题，再协调分组与责任”的方案，不继续完善这套业务协议。历史调用记录保留；可复用的原生结构化提交、原响应保存和本地重放能力不随业务协议一起丢弃。

唯一目标流程：

`读取计划书 -> 理解项目结构 -> 按现有专业能力目录组队 -> 单一强模型生成全局有序问题列表 -> 代码取前 N 项并派工 -> 专家评审 -> 综合与交付`

专家不参与题目生成。评审维度继续用于描述和综合，但不作为组队席位或出题分区。不增加去重模型、语义查重器、自动改写、质量裁判、补题或重抽循环。

## 当前实现依据

- `src/spacebio_review/v4/preparation.py` 的 `map_project()` 同时理解项目和输出 `questions`。
- `run()` 将初始问题取出后，逐个调用 `orient()`，把每位专家的 `proposals` 追加到同一列表。专家没有完整的累计问题清单。
- `allocate()` 再决定合并、撤回、延期与多成员责任；`planning_preparation.py` 候选仍继承上述提问入口。
- mytest22 的 6 个初始问题与 5 位专家各 3 个问题最终形成 21 个提案，成像能力问题重复出现。修复点首先是生成职责，而不是改一个合并字段。

## 输入准备

保留现有申请读取、自然段/完整方案读取、来源定位和专业能力目录。`map_project()` 只输出科学目标、研究路径、活动、观测产物、主张、依赖与理解限制，删除 `questions`。不把 map 改造成隐藏的候选题清单。

组队仍基于项目结构和 `ExpertiseCatalogue`，保留 `purpose`、`profile_ids`、方法技能及 `model_tier` 等现有职责。一个专家可以组合相关学科与方法能力。组队不顺带出题，不因题数上限凑人数。

删除专业定位调用及其 `understanding/corrections/proposals` 提交。专家原本承担的材料理解不是丢弃：全局问题生成者读取计划书，专家在正式研究中仍可回读、纠正题目前提并说明适用条件，但不能另建评审题。

问题生成者一次获得：

- 完整的激活专家配置投影：程序 ID、专业标签、职责和方法能力。不能只给专家编号，也不附所有专家技能全文。
- 不含候选问题的项目结构及现有理解限制。
- 按原顺序提供的完整计划书自然单元和必要表格/图注。正文每个单元只展开一次，来源 ID 使用既有材料身份；项目映射中的来源只给定位，不再展开同一段原文。
- 既有评价原则及本文的出题标准。

不输入旧问题池、历史分配计划、其他专家定位输出、历史请求链或报告。验收复用旧项目映射时，必须剥离旧题目、定位纠正和分配结论，并与原计划书对照。

默认使用完整计划书的单次全局生成，不按专家或章节分别出题再拼接。发送前沿用现有上下文容量预览。若完整输入超容量，本轮明确停在生成前并报告，不静默截正文、不临时增加摘要 Agent、不自动退回分段出题。超长材料策略暂留待后续明确需求，不宣称已覆盖。

## 问题生成 Interface

实现一个独立、可局部调用的 `QuestionGeneration` Module，输入为项目、原材料视图、激活专家；输出为一个全局排序的 `questions` 数组。正式派工数量上限不是该 Interface 的模型输入。

每项只承担必要的科学表达与唯一归属：

| 字段 | 职责 |
|---|---|
| `expert_id` | 从本次已激活专家中选择一位负责专家 |
| `question` | 一个完整、可评审的核心判断问题 |
| `scope` | 此题覆盖的对象、阶段、条件和不承担的相邻判断 |
| `importance` | 对项目核心判断的重要性理由，不是重复的数值排名 |
| `changes_judgment_if` | 哪类可能结论会改变对项目的评价 |
| `information_route` | 当前可采取的分析、核对或检索路径，不是未来实验清单 |
| `aspects` | 相关评审维度标签，可多选，但不重复生成同题 |
| `evidence_handles` | 对应计划书来源选择，绑定复用现有来源设施 |

数组顺序就是全局重要性顺序。程序生成正式题号和原始序位；模型不填题号、名次、任务 ID、组 ID、成员列表、合并关系或调度状态。`questions` 不设 `maxItems`，也不按专家分成多个独立排序列表。

一个问题只有一位负责专家。跨学科判断优先交给配置中具备相关组合能力的专家，不能因多个专家都能分析，就重复起题。若确实存在可独立改变评价的不同判断，才拆成不同问题。无法由已激活能力开展的判断不伪装成已覆盖；不临时激活额外专家或转交另一个分配模型。

## 提示词必须明确的出题标准

以下要求应落实为实际系统提示，而不是只放在设计文档里。

### 粒度

- 一题围绕“对象/过程 + 条件 + 需要形成的评审判断”，应能产出一段或一组连贯的专业论证。
- 不以章节标题、学科名称或“请全面评价可行性”作为题目；也不把一个判断所需的逐项参数核对、搜索词、对照项分别变成题目。
- 判断是否需要拆题，依据子部分能否形成不同的项目评价及独立的分析路径；不能仅因指标、材料、阶段名称不同而拆。
- 服务于同一判断的条件、指标和替代解释保留在同一题内；不能为了题面短而切断条件。
- 一题不包办全项目。即使专家同时懂统计、管理，也不能把实验设计、经费、排期和生物机制装进一个总问题。

### 不重合的程度

- 在一次全局理解中划定每道题独有的判断责任，再形成最终列表。不同题不能换措辞重复问同一个结论，也不能把一题的主要分析作为另一题的主要分析。
- 不因不同专家、不同维度标签或不同来源重复生成同一判断。
- 可以共享背景、原始材料和必要前提；不要求科学上完全独立，也不要求引用来源互斥。
- 题目应可凭计划书和可获得资料独立开始分析，不把“先等另一位专家产出答案”作为正常执行前置条件。
- 相邻问题涉及同一对象时，在 `scope` 中说明本题具体判断边界，不通过引用未生成的题号或建立依赖图来划界。

### 忠实于计划书与可研究性

- 按计划书实际的地面/在轨分工、观测阶段和目标起题，不把常见教科书要求强加成项目承诺。
- 未给定的设备参数可以是待核实条件，不能先认定设备不够用；正向贡献、可成立条件与风险都可成为评审内容，不预设必须批评。
- 缺最终实验结果不等于当前不能评审。可以研究方法合理性、测量范围和先例；必须由未来实验获得的事实留作判断条件，不生成“现在必须获得未来结果”的伪任务。
- 不以申请中的“首创”等自述作为已核实前提。

### 排序与数量

- 对整个项目按重要性从高到低排序，不先按专家、章节或评审维度分组。
- 优先比较对核心科学价值、结论成立条件和实施成败的影响，再比较作用范围和当前分析对判断的帮助；不按易答程度或检索方便程度排序。
- 不给题数目标、上限、下限、每位专家配额、“大约若干题”或预算暗示。不把代码的 `max_questions` 或剩余任务数放入提示词。
- 题目数量由实际可区分的判断决定。字段表达简洁完整，生成后直接提交，不输出自检报告或逐项去重过程。

### mytest22 的定向示例

旧 q8/q12/q17/q19 不能以四种近似说法重复承担“在轨成像是否支持目标动态观测”的责任。一个合理题面示例是：

> 现有在轨成像条件能支持计划书拟观察的生长、粗化及相互作用阶段的哪些定量结论，适用边界是什么？

分辨率、时间采样和目标尺度是这个判断的分析内容，不自动变成三题。原材料若明确成核研究在地面完成，就不能预设在轨必须完整捕捉成核。备选装置的资源可获得性若是独立实施判断，可以另题，但不能再次做一遍相同的成像能力论证。具体归属依据本次激活专家，示例不硬编码 expert-1。

## 模型与协议

新增独立 `question_generation` 路由。优先复用 `config/planning.yaml` 中已有局部原生 schema 实测基础的强模型和 Messages Adapter，不把 JSON 文本模式或 prompt 中贴 schema 当成同等替代。具体新契约仍须通过 Change 36 的局部探针。

只迁移可复用的传输与提交能力，不继承 `joint_work`、required 问题槽、路由工作集、read_context 或增量规划动作。该环节默认一次正式生成；修复、截断续写、HTTP 自动重试均不增加。专家、检索、综合、写作路由保持现有设置，不扩大之前仅对专业正式提交的托管模型授权。

模型服务的 token 上限是输出容量，不是题目数量约束。遇到截断不得解析前半张题单冒充生成完成，保留真实失败，改进职责/表达后按另一个版本验证。
