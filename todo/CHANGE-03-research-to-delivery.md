# Change 03：停止探索后，完成研究提交与报告输出

状态：代码实施与局部回归完成；真实探针完成六方面综合，但完整交付验收未通过（详见末尾）。依赖 change 01、02。这一步解决 mytest16 的流程中断，不能被前两步的请求下降替代。

## 失败链与目标

mytest16 的账本达到 600 次：375 次 embedding、225 次其他模型请求。16 份专家产物已产生，另外 6 个专家任务失败；六方面综合的第一次请求均被拒绝。`Synthesis.run()` 吞下各方面的具体失败后，`overall()` 又抛出 `no_professional_basis_for_assessment`。

当前同时存在三处问题：不同成本的请求抢同一计数；初始研究和补研没有保护后续输出；已有局部收束机制只关注当前任务轮数，没有接入全局余量。`runner.py` 的总超时包住整个评审，也不能等到总超时发生后才开始报告。

目标是让正常资源边界触发“已有研究正式提交 → 按实际覆盖综合 → 交付”，保留未评范围与开放问题。不是把 partial 改成 completed，也不是保证在服务不可用或额度本来就不足时凭空生成完整报告。

PaperQA 的参考点是探索超时/步数截断后仍调用答案生成：[主流程](https://github.com/Future-House/paper-qa/blob/57e89f7223b0960d5ee5ea048c69e3c47e088572/src/paperqa/agents/main.py#L151-L179)。这里复用本项目的正式提交与六方面报告，不另造简版科学结论。

## 一、预算只作必要拆分

1. 保留唯一 `Budget` 和原请求账本。`max_model_calls=600` 明确定义为生成模型的 provider 尝试数，包括专家、重排、子研究、综合、写作和重试。
2. 新增 `max_embedding_calls=600`，单独限制实际 embedding 批次和重试，允许设为 0 以关闭真实向量请求。缓存命中不计请求。这个数先保持原总上限的量级，不靠无限放大限制解决问题。
3. 请求行仅增加一个内部 `kind: model | embedding`，在 `Budget.reserve()` 按调用入口确定，不能依赖模型名字猜测；不需要模型输出或维护该字段。
4. 时间、可选输入/输出 token 上限继续约束整体，不能因拆开计数而绕过。拆分后总 HTTP 尝试上限不再是 600，配置注释和调用统计必须明确这个行为变化。
5. embedding 达到自身上限时，当前混合召回可使用已有词法回退；不能把全局生成预算也判为耗尽。若全局已要求停止探索，则直接收束，不再借回退继续大范围搜集。

不引入加权积分、费用汇率表、每专家预算字段或多个账本。旧预算缺少类别不能按新语义猜测恢复；新增配置会进入 `runner.py` 已有的配置 manifest，利用其不匹配拒绝旧运行续跑。不要为了预算修改不可变研究产物的 `Records.VERSION`，以免连旧产物只读重放也被阻断。旧运行只读、不迁移；局部探针必须新建账本，不能直接给旧行补类别后伪称续跑成功。

## 二、给后续输出保留一段容量，复用原有 closing

只新增两个运行级配置：`completion_reserve_calls` 和 `completion_reserve_seconds`，初始候选分别为 80 次生成请求、1,800 秒。它们是从原总额里保留的份额，不是额外额度；需在下述局部验收中核对实际余量，记录最终取值。

### 1. 停止新工作，同时让已启动任务能提交

- 由 `Budget` 提供一个统一的探索可用性判断，供初始任务启动、工具探索、委派和补研路由共用；不要在多处复制减法。
- 在固定的后续输出预留之外，还需要保护正在运行的研究任务的正式提交。按实际活跃父/子研究任务及现有正式修复、截断恢复、provider 重试上限计算一个小的内存预留总量；开始前登记、`finally` 释放，不持久化第二套任务表。
- 示例边界是：剩余生成调用数减去后续输出预留、活跃任务提交预留后，不足以启动下一次探索，就停止探索。任务调用上限必须包含 provider 重试；不能把一次正式任务简单当成一次 HTTP 请求。
- 如需区别探索与正式提交权限，使用一个任务局部的内部调用上下文，正式提交只可消费自己的收束空间，不能侵占其他活跃任务和后续输出的预留。已消耗的提交名额从该任务的剩余预留中扣除，避免重复保留；退出任务后释放未使用部分。不要通过模型任务名猜测当前是否正式提交，也不要新增模型 schema 字段。
- 接入 `AgentRuntime` 现有 `closing` / `phase()` 和正式提交函数。全局收束后停止新搜索、向量批次、重排和委派；基于已经返回的资料完成正式产物。避免先请求一轮“请确认提交”又把最后的正式输出额度耗掉。
- provider 发送前仍是唯一原子记账点。工具内部多批 embedding、并发任务和子研究都要经过同一个判断；只在工具外层判断一次不够。

这里的内存登记只表达资源责任；继续使用原有任务状态、现有 `reason` 和阅读记录，不新增 `draining`、`settling` 等持久化状态。

### 2. 在总时间到期之前停止探索

- 总运行时间上限仍然有效；不在收束时重置时钟或关闭总超时。
- 探索在 `remaining_seconds <= completion_reserve_seconds` 时停止启动。正在等待网络的探索请求应限制为剩余探索时间，超时取消后转正式提交；确保不会仍有后台工具继续写结果。
- 正式提交和后续综合使用剩余总时间。真实 provider 延迟无法完全预测，预留是正常路径保障，不是无条件完成承诺。
- 可选 token 总额仍是硬约束；有配置时，用已有请求估算与当前任务输出上限保护收束空间。若连最低综合输出空间都不足，提前明确停止并保留产物，不宣称仅靠调用数预留即可保证成功，也不自动提高 token 上限。

## 三、由调度器走完现有交付路径

- `Coordinator.research()` 的队列任务必须在真正取得并发槽、准备启动时重新检查探索额度，避免排队时额度充足、执行时已耗尽仍启动。
- 为降低多个相近问题先耗完额度的风险，初始队列采用简单确定性顺序：先安排能为尚无已完成产物的适用方面提供覆盖的现有任务，再按原顺序；不新增 LLM 派工、优先级评分字段或优化器。排序只改善机会，不能把安排过等同于已评估。
- 未启动的工作使用既有 `deferred` 和明确原因保存，覆盖仍显示未完成；下次循环不能自动把这些工作重启。已启动任务的有限结论与未知通过原正式产物保存。
- 全局进入收束后，不调用模型继续分类一大批补研请求；`route_requests()` 直接沿用既有延期处理，交付保留请求原文、未解决范围和延期原因。
- 研究任务结束后，仍执行现有方面综合、总体综合、冻结、`Delivery.assemble()`、中文摘要和英文翻译。无研究依据的方面如实标未评，不能造一个空方面结论充数。
- 80 次预留是起始工程参数，不是“所有报告最多 80 次”的证明。检查当前六方面/总体综合的可能归并、正式修复以及实际翻译分片需求；不允许补研或重复综合占用最后一轮交付需要的空间。报告特别长或硬限制不足时保留已有中文正文和专家附录，翻译显示 partial；复用 `Delivery.run()` 已有的先导出再翻译行为。
- `Synthesis.run()` 若没有成功方面综合，应携带原始方面错误和已有专业产物数量向上传递；只有确实没有专业产物时才能说缺乏专业依据。不增加错误包装状态机，也不伪造成功。

## 实施记录（2026-10-08）

- `Budget` 的唯一账本新增内部 `kind`，生成和向量请求分别计数；重试仍由原 provider 在发送前逐次记账。删去旧的单独 `admission_reason()`，探索准入统一使用 `exploration_reason()`。
