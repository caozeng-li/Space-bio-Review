# 本地模型选型与评审任务适配调研

调研日期：2026-10-10。依据当前代码与官方模型资料；暂不考虑 GPU 限制，以评审质量和任务适配为优先。本次没有下载模型、修改配置或运行评审。以下是值得优先验证的选型判断，不是本项目上的实测排名。

## 1. 我的建议

**首选试验组合：Kimi-K3 做专业研究与图文阅读，DeepSeek-V4-Pro 做项目理解和综合判断，Qwen3.8-27B 做辅助任务及摘要翻译，Qwen3-Embedding-8B 做本地向量检索。** 专用 Qwen3-Reranker-8B 可以随后接入，但当前实现不能仅通过替换模型名使用它。

这不是因为三个生成模型分别掌握三个互不重叠的知识领域，而是它们适合承担不同工作：深入查读与研究、跨专业整合与取舍、较明确的材料筛选与表达转换。多个专业智能体可以共享同一模型，不需要给类器官、线粒体、统计、空间设施等分别部署一套专用权重。专业性主要来自任务、方法、原始材料与研究过程。

如果希望先把变量控制住，**第一轮只部署 Kimi-K3、DeepSeek-V4-Pro 和 Embedding-8B 也可以**，辅助任务暂时共享主模型。第三个生成模型的目的主要是降低大量简单请求的等待时间，不是构成 MAS 的必要条件。

另保留一套迁移基线：**DeepSeek-V4-Pro + DeepSeek-V4.1-Flash + Qwen3.5-397B-A17B + Qwen3-Embedding-8B**。它与当前配置的模型家族一致，便于区分“本地推理服务的变化”和“更换模型带来的变化”。当前配置使用这些家族，不代表已经证明其本地权重在本系统中可靠，也不保证托管版本与下载版本完全相同。

这里把“可下载权重并本地推理”与“Apache/MIT 等宽松许可证”分开。Kimi-K3 和部分最新 Qwen/GLM 使用自定义许可证；如果要求严格限定宽松许可，优先采用后文的 DeepSeek/Qwen3.5 组合。

## 2. 当前任务到底需要什么能力

本节以实现为准，主要核对了 [运行配置](../config/runtime.yaml)、[研究配置](../config/review.yaml)、[项目理解](../src/spacebio_review/v4/preparation.py)、[研究执行](../src/spacebio_review/v4/research.py)、[综合](../src/spacebio_review/v4/synthesis.py)、[交付](../src/spacebio_review/v4/delivery.py) 和 [文献研究](../src/spacebio_review/evidence/literature.py)。

| 环节 | 实际工作 | 对模型的要求与选型影响 |
|---|---|---|
| preparation | 分批读申请，理解目标、活动、观测与依赖，配置专家，组织研究范围 | 需要强理解与规划能力；初始理解错误会影响后续研究，不宜当普通摘要任务降级 |
| literature | 生成与调整检索、取文献、阅读正文和图像、形成有来源的研究结果 | 需要多轮工具使用、跨论文比较、识别实验条件，属于核心难点 |
| specialist | 把领域知识与项目具体设计联系起来，判断贡献、局限、替代解释和研究需求 | 需要强通用科学推理；会答医学选择题不足以胜任 |
| assessment | 按方面综合完整论证，再形成总体建议和支持条件 | 需要保留限定、区分局部不足与整体价值，不能靠投票或机械合并 |
| visual | 阅读论文图表、装置和图像材料 | 需要真正支持图像输入的模型；文本旗舰不能因参数更多而替代视觉输入 |
| writer | 生成决策摘要、翻译中文主报告 | 当前中文主体由程序装配，writer 不负责重新创造全部科学判断；重点是完整、忠实和术语准确 |
| admission / query / rerank | 最低准入、检索表达、候选相关性筛选 | 相对明确，可共享辅助模型；准入和筛选仍须避免误删有效材料 |
| embedding | 对材料与查询生成向量，参与混合检索 | 独立专用模型，不需要生成式旗舰执行 |

任务的难点是**读懂一个尚未完成的科学项目，并利用外部知识判断它能产生什么认识及价值**。这涉及跨文献迁移、实验设计与测量含义、空间实施条件，以及正面价值和局限的共同判断。它既不是单纯信息抽取，也不是只要求推理链闭合。

因此，不建议把 7B–14B 医学模型或推理蒸馏模型作为默认主评审模型。27B–35B 通用模型可以作为辅助和对照，但在不受硬件限制时，没有理由预先假定它们能保持旗舰模型的专业研究质量。反过来，参数最大也不是可靠的质量证明。

**上下文方面**：当前研究、文献和交付的软目标约为 64,000 tokens；正式输出部分路由达 24,576 tokens。64K 是上下文组织目标，不是所有真实请求的硬上限。选择支持 256K 或更长上下文的模型较合适，但应以实际服务窗口、完整输入、工具定义与输出预留共同计算容量；不能把模型卡上的最大长度理解为所有材料都应一次塞入。

## 3. 候选模型与适用位置

### 3.1 Kimi-K3：优先试验的专业研究模型

官方开放图文模型，约 2.8T 总参数、104B 激活参数，原生约 1M 上下文，采用 Kimi K3 自定义许可。模型卡包含 ResearchRubrics、DeepSearchQA 与工具使用评测；这些方向比单纯代码榜更贴近本项目的研究环节，所以我把它放进首选，而不是仅依据发布时间。[官方模型卡](https://huggingface.co/moonshotai/Kimi-K3)

推荐用于 literature、specialist 和 visual；也值得与 DeepSeek-V4-Pro 比较总体综合。暂时采用两者分工，是一个待验证的工作假设，不是已经证明“Kimi 善研究、DeepSeek 善判断”的固定规律。若 Kimi 在两类局部任务上都更好，可以统一使用它，没必要为了异构而异构。

接入时有一个实质要求：K3 始终启用 thinking，并要求多轮工具流程原样回传包含 `reasoning_content` 和 `tool_calls` 的完整 assistant 消息，思考强度为 low/high/max。当前 provider 的 `model_dump` 已保留扩展字段，这是有利基础；仍需核对上下文重建和正式提交阶段，不能只改模型名就认定兼容。[官方使用说明](https://huggingface.co/moonshotai/Kimi-K3#6-model-usage)

### 3.2 DeepSeek-V4-Pro：综合与项目理解的优先基线

官方开放文本模型，1.6T 总参数、49B 激活，支持约 1M 上下文，MIT 许可。模型卡给出了知识、推理和长上下文能力评测以及本地推理说明。[官方模型卡](https://huggingface.co/deepseek-ai/DeepSeek-V4-Pro)

它已经对应当前 coordinator/strong 路由，适合作为本地 preparation、assessment 的第一基线；也应参与关键 specialist 片段的比较。保留它的理由包括当前角色匹配和较全面的能力证据，不等于其科学判断已获验证。

常规复杂工作先比较 High；对真正困难的综合再比较 Max。官方对 Think Max 建议至少 384K 服务窗口，不能在很短的总输出额度下假定获得官方 Max 表现。也不应给每次候选筛选开启最高强度。[本地运行建议](https://huggingface.co/deepseek-ai/DeepSeek-V4-Pro#how-to-run-locally)

### 3.3 DeepSeek-V4.1-Flash：值得保留的研究模型候选

官方版本原生支持图文和约 1M 上下文，模型卡区分 552B backbone 与额外 196B Engram 条件记忆，并区分 prefill/decode 的激活量；不能把“8B 激活”理解为一张小卡上的 8B 模型。许可为 MIT，推理强度支持整数 1–100。[官方模型卡](https://huggingface.co/deepseek-ai/DeepSeek-V4.1-Flash)

它是当前 research 路由对应家族，适合成为 Kimi-K3 的主要研究环节对照，也可以承担视觉。Flash 名字不意味着专业能力弱，也不意味着必然比 Pro 更适合所有判断。其新架构和工具评测值得关注，但本项目需要比较的是文献使用与研究结果，而不是代码代理得分。

### 3.4 Qwen3.8-2.4T-A95B：应比较的旗舰，不直接宣布取代 DeepSeek

官方开放权重为纯文本、始终启用思考、2.4T 总参数/95B 激活，原生 262,144 上下文，可扩展；使用 qwen3.8-max 自定义许可。值得拿来比较项目理解、专业解释与综合。[官方模型卡](https://huggingface.co/Qwen/Qwen3.8-2.4T-A95B)

需要特别区分：模型卡明确说明托管 Qwen3.8-Max 额外提供视觉、非思考模式等能力，评测表也使用 Max 名称。因此，不能把这些能力和全部成绩直接写成本地 checkpoint 的能力。它适合作为优先挑战者，是否替换主综合模型由相同上下文的局部结果决定。

### 3.5 Qwen3.8-27B / Flash-Next：辅助生成与吞吐候选

Qwen3.8-27B 支持图文，原生 262,144 上下文，Apache-2.0 许可；推荐先用于 query、生成式 rerank、摘要和翻译。在摘要中丢失关键支持条件或改变判断强度时，应将该任务保留给主模型，而不是继续堆补救提示。[27B 官方模型卡](https://huggingface.co/Qwen/Qwen3.8-27B)

Qwen3.8-Flash-Next 同样支持图文、原生 262,144 上下文和思考/非思考模式，使用 qwen-community-1.0 许可。可作为更强辅助模型或研究模型对照；但既然主组合已经有两套旗舰，第一轮不必再部署它。[Flash-Next 官方模型卡](https://huggingface.co/Qwen/Qwen3.8-Flash-Next)

当前 Qwen3.5-397B-A17B 仍有基线价值：397B 总参数、17B 激活、图文、原生 262,144 上下文、Apache-2.0。选择它可以减少迁移时的模型变化，而不能因为出现了 3.8 就不经比较直接废弃。[官方模型卡](https://huggingface.co/Qwen/Qwen3.5-397B-A17B)

### 3.6 GLM-5.3 / GLM-5.3-Flash：候选，但目前不排在首选组合

GLM-5.3 的官方材料重点是编码和长程任务；Flash 为原生多模态，官方介绍为约 320B 总参数、18B 激活，并提供本地推理框架入口。它们值得做工具流程与研究片段的替代实验，但不能从代码能力直接推出科学评审优势。[GLM-5.3](https://huggingface.co/zai-org/GLM-5.3)、[GLM-5.3-Flash](https://huggingface.co/zai-org/GLM-5.3-Flash)

没有把所有开放模型都列为推荐。当前最需要的是选出少量可信候选，在本系统的关键工作上比较；增加更多常驻模型、仲裁代理或多轮互审，不是本次选型的目标。

## 4. 领域微调是否更合适

### MedGemma：可试验的医学顾问，不宜直接替代主专家

MedGemma-27B-text-it 针对医学文本，适合试验医学概念解释和已有证据下的局部专业意见。模型使用 HAI-DEF 相关条款，并非 Apache/MIT；官方明确写明没有针对多轮应用评估或优化。[模型卡及限制](https://huggingface.co/google/medgemma-27b-text-it)

本项目中的类器官、线粒体、空间培养和实验设计，与临床问答只有部分重合。可以给它一个自包含的专业问题及已取到的材料，比较它是否补充了通用模型漏掉的重要知识；没有必要先让它承担文献搜索、工具循环、研究提交和总体评审。

### OpenScholar-8B：任务贴近的专用对照，比泛称“医学模型”更有参考价值

OpenScholar-8B 是基于 Llama-3.1 的科学文献综合微调模型。研究本身覆盖跨论文综合、引用与检索，和 literature 环节相近。[官方权重](https://huggingface.co/OpenSciLM/Llama-3.1_OpenScholar-8B)、[作者论文](https://www.nature.com/articles/s41586-025-10072-4)

应将它放在“给定一组论文片段，能否形成可靠专业综合”的局部对照中。论文中的系统效果还包含语料、检索器和工作流，不能把成绩全部归因于 8B 权重，更不能推定优于当前旗舰在中文项目评审上的表现。其 Llama 派生许可也应与 Apache/MIT 分开。

### BioMistral / BioReason：领域相关不等于任务匹配

BioMistral-7B 是医学领域模型，可以作为旧一代领域适配基线，不推荐在无限制条件下作为主研究模型。[官方项目](https://huggingface.co/BioMistral)

BioReason 研究的是结合 DNA 表征的生物推理。当前系统主要处理项目书、论文、图表和专业分析，并不直接输入 DNA 序列完成预测，所以它不是可直接替换的 specialist 模型。[作者论文](https://arxiv.org/abs/2505.23579)

**领域微调值得研究，但应让它证明在真实专业任务中提供了额外价值。** 本次没有找到足够证据，支持把某个面向空间生物学项目评审的专用模型列为成熟首选；这不等于断言此类模型绝不存在。若以后自己微调，优先收集“项目材料 + 外部证据 + 专家解释”的优质样本，而不是只训练报告格式或只加入医学考试题。

## 5. 推荐的三种组合

### A. 质量优先的新组合：建议首先做局部试验

| 当前路由/功能 | 建议模型 | 使用方式 |
|---|---|---|
| preparation、assessment、strong | DeepSeek-V4-Pro | High 起步；重要综合比较 Max；Qwen3.8-2.4T-A95B 和 Kimi-K3 为替代候选 |
| literature、specialist | Kimi-K3 | 完整专业研究，保留工具历史，给予足够的推理与正文预算 |
| visual | Kimi-K3 | 复用研究模型，不必额外增加视觉服务 |
| admission、query、现有生成式 rerank | Qwen3.8-27B | 明确、有限的工作；第一轮也可暂时复用主模型 |
| writer | Qwen3.8-27B | 摘要与翻译；复杂摘要的忠实性不够时改用主模型 |
| embedding | Qwen3-Embedding-8B | 独立本地部署，与生成模型分开 |

这是我的首选**试验方案**。其中模型分工来自任务适配推断，尚无本项目结果证明混合方案优于单一旗舰。比较后如果同一个模型在研究和综合上都占优，就合并，不保留无收益的异构设计。

### B. 迁移优先组合：先保持现有模型家族

DeepSeek-V4-Pro 负责 preparation/assessment；DeepSeek-V4.1-Flash 负责 literature 和辅助研究；Qwen3.5-397B-A17B 负责 specialist/visual/writer；Embedding-8B 本地化。

优势是实验变量少，而且这些主模型的官方许可证为 MIT 或 Apache-2.0。适合先回答“当前框架在本地服务上能否保持输出能力”，再逐步比较 Kimi-K3 与 Qwen3.8。部署时仍要固定权重 revision、模板和推理引擎，不能把相同家族名视为与托管服务完全相同。

### C. 简化组合：少模型、完整工作流

DeepSeek-V4-Pro 负责全部核心文本工作；DeepSeek-V4.1-Flash 负责工具研究、图文和辅助工作；Embedding-8B 负责检索。

如果希望控制服务种类，这套更直接。没有证据表明必须使用多个厂商的模型才能形成有效 MAS，也没有理由为“专家差异”额外引入投票和辩论流程。可将它作为 A 的必要对照。

## 6. 检索模型应独立选型

不考虑 GPU 时，首选 **Qwen3-Embedding-8B**；它支持多语言、32K 输入和最高 4096 维向量，也支持缩减维度。中英混合检索与本项目相符。4096 维可以作为质量起点，但是否优于当前 1024 维必须在真实查询上比较，不是维度越高越能保证质量。[官方模型卡](https://huggingface.co/Qwen/Qwen3-Embedding-8B)

**Qwen3-Reranker-8B** 是值得增加的专用候选相关性模型。[官方模型卡](https://huggingface.co/Qwen/Qwen3-Reranker-8B)

这里有两处具体适配，不能只替换配置中的名字：

1. [当前排序](../src/spacebio_review/evidence/retrieval.py)调用聊天模型，要求生成 `{"ids": [...]}`；专用 reranker 按 query-document 对评分，接口和输出含义不同。未来只需在排序入口适配评分及多查询合并，保留 BM25 与 dense 的候选并集，不必改整个研究流程。接入前沿用生成式排序即可。
2. [当前向量层](../src/spacebio_review/models/embedding.py)有模型、端点、维度参与的缓存标识。更换权重、查询指令或编码方式时，要让旧缓存与新向量分开；同样是 1024 维也不表示属于同一向量空间。Qwen 的查询侧任务指令、池化和归一化应按官方方式实现，不能只接通 `/embeddings` 就认定检索等价。

当前配置中的 `text-embedding-v4` 是托管服务名称；配置也明确没有声称它与 Qwen3-Embedding-8B 权重完全相同。质量判断应包含关键证据是否进入候选，而不只看向量调用是否成功。

## 7. 本地化时真正需要适配的边界

用户所说“不使用 API”，这里理解为不调用外部托管模型。推理服务可以完全运行在本机/内网，通过本地 HTTP 接口与现有程序通信；不需要为了去掉远程服务而把所有权重直接塞进评审进程。如果连本地服务接口也不使用，则要实现现有 `ChatModel.complete` 的进程内后端。

[当前 provider](../src/spacebio_review/models/provider.py)虽然名为 `DashScopeModel`，实际上使用可配置 `base_url` 的 OpenAI 客户端。可复用这一调用边界，但要处理以下几件实事：

- **模板与参数对应。** 当前配置有百炼的 `enable_thinking`；本地 Qwen 示例通常使用 `chat_template_kwargs`，Kimi 使用其自身思考参数。正式提交路由也有覆盖项，不能只修改普通路由。[Qwen 官方本地调用示例](https://huggingface.co/Qwen/Qwen3.6-35B-A3B)
- **多轮消息保留。** 核对实际 assistant/tool 消息流，尤其 Kimi 的完整思考历史要求；上下文重建后需要形成符合模型模板的新会话，不能残留半截工具对话。
- **给正文留下生成空间。** 当前额度同时受推理消耗与正文影响。开启更强 thinking 却不调整额度，仍可能得到没有完成的报告。应观察真实 `finish_reason`、推理长度和正文长度，再确定各任务的生成配置。
- **本地结构化生成能力。** 工具调用、JSON object、受约束 schema 是不同能力，要按所选引擎的实际支持接入；不应继续沿用远程服务的能力声明，也不需要额外堆叠多层校验。
- **保留合理上下文与调度。** 长上下文能力用于容纳必要论证和限定，不用于重复累积全文；四个并发研究任务需要实测吞吐和等待时间。没有外部限流后，仍存在显存、计算和长输出占用。

本地化模型推理不等于断网。当前文献发现仍访问 Europe PMC、OpenAlex 等外部资料服务；若未来要求完全离线，需要另建本地文献库和检索入口，那是独立任务。

部署参考优先使用模型作者链接的引擎配方，例如 [Kimi-K3 的 vLLM recipe](https://recipes.vllm.ai/moonshotai/Kimi-K3) 和 [Qwen3.8 旗舰的 vLLM recipe](https://recipes.vllm.ai/Qwen/Qwen3.8-2.4T-A95B)。前者还记录了偶发工具格式与解析器不匹配的情况，这正是需要真实局部工具循环的原因；接通聊天接口不能代替这一验证。

## 8. 怎样用少量真实任务作出最后选择

不先跑完整评审，也不把历史测试目录作为选型依据。构造少量有真实上下文的局部任务，给候选提供相同申请材料、相同证据与相同工具条件。建议先做以下六组：

| 局部任务 | 重点观察 |
|---|---|
| 项目理解与专家配置 | 是否读准目标、研究路线和实际观测，是否提出有价值的专业研究方向 |
| 创新性文献比较 | 是否区分正常/肿瘤类器官、模拟/真实空间环境，找到增量而非只否定“首次” |
| 测量与实验设计分析 | 是否准确理解 DCF、Fluo-8、类核图像等证据能说明什么，同时提出可行改进 |
| 平台与可行性研究 | 能否从已有培养和成像条件识别支持基础，进一步讨论适配需求，而非机械要求资源证明 |
| 跨专业综合 | 能否同时保留价值、可行性和设计局限，提出有重点的推进条件，避免重复堆砌 |
| 摘要、翻译与图表理解 | 是否完整保留判断和限定，图表是否读对，表达转换是否引入新结论 |

其中研究任务分两步：先固定证据包比较科学分析能力，再开放同样的本地工具比较自主研究能力。这样可以区分“没有找到资料”和“拿到资料仍然理解错了”。检索模型则单独比较关键文献/段落是否进入候选。

主要由人盲评：新增知识与洞见是否有用、项目价值是否被发现、专业理解是否准确、文献比较是否恰当、建议是否可执行。再记录依据使用、限定保留、重复程度和交付完整性。工具调用正确率和耗时是必要的运行指标，但不代替评审质量。无需事先发明复杂加权总分。

有条件时对关键片段重复少量次数，避免被一次偶然好输出误导。比较时同时记录权重 revision、模板、思考强度、输出额度和输入长度；不要把一个模型的充分推理与另一个模型被截断的结果作为公平比较。

**实际选型顺序：先建立当前模型家族的本地基线，再比较 Kimi-K3 的专业研究、Qwen3.8 旗舰的综合能力，最后决定是否保留辅助生成模型和领域微调模型。** 先把专业研究与综合做好，其他模型围绕这两件核心工作服务。
